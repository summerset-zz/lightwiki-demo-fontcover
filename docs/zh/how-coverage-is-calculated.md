这个字体覆盖了哪些字符，在本站是**现算**的，不需要重新解析字体、不需要联网、也不需要重跑同步。原因很简单：需要的两份数据都已经在手上，而且都是纯数据。

## 两个输入 {#inputs}
<!-- hint: 覆盖 | 前一个数字是 cmap 声明的码位总数，后一个数字是这些码位合并成的连续区间段数。 -->

1. **字体的码位区间**（`cmapRanges`）：分析字体时从 `cmap` 表里抄出来的区间，压成 `[起, 止, 起, 止, …]` 的扁平数组存进档案。CJK 字体大约几百段；
2. **区块表**：Unicode 官方 `Blocks.txt` 解析出来的三百多个区块，外加每个区块的已分配数，服务端缓存着。

一个在浏览器（本机字体档案）或 API 响应里，一个在 `/api/unicode/blocks`。两边都是数组与数字，遍历一遍就出结果。

## 分子：区间与区块求交 {#numerator}

对每个区块，数有多少个码位同时落在字体区间里、又落在这个区块里。

实现是**一趟归并**：区块与区间都是升序的，所以用一个游标在区间数组上往前走，每个区块只从上次停下的地方继续看。整体复杂度是区块数 + 区间数，不是区块数 × 区间数。

（浏览器与服务器用的是同一份实现。）

## 两个分母 {#denominators}

| 数字 | 分母 | 用在哪 |
| --- | --- | --- |
| `covered / assigned` | 区块里**已分配**的码位数 | 显示在区块行上 |
| `ratio` | 区块的**总大小** | 进度条的宽度 |

为什么分开，见 [区块与已分配](/docs/unicode-blocks)：一个 CJK 区块两万多码位里大量是未分配，用总大小当分母，条会显得无关紧要；而用已分配当分母，才能看出这个字体到底漏了多少该有的字。

## 面板顶部那两对数字 {#panel-totals}

区块列表上方还有两组数字，分母与区块行不同，都不是某一个区块：

| 显示 | 分子 | 分母 |
| --- | --- | --- |
| `码位数 30,890 / 172,808` | 这个字体的 `cmap` 区间一共声明了多少码位 | **全部区块的已分配总数** |
| `区块数 61 / 353` | 有覆盖的区块个数 | **区块总数**（现在是 353） |

两个都要读成“占全站的比例”，而不是“占这个区块的比例”，后者才是区块行上的 `covered / assigned`。

三点如实说明：

- 别把“区块”和“区间”混起来：一个区块里可能落着很多段 `cmap` 区间，而“区块数”只数区块；`cmap` 的区间段数是另一个数，本站没显示；
- 第一行的分子是“区间宽度之和”，所以它包含字体声明了但没有名字的码位（私用区、还没分配的区间都可能被声明），而分母只数已分配的。两个口径并不严格对齐，所以这个比值只能当量级看；
- 两个分母都随 Unicode 版本变（新增区块、新分配码位），所以这两个数字适合横向比字体，不适合跨年份比。

## 三个限制（如实说明）{#limits}

1. **映射到非 0 字形就算覆盖**。分析时已经把映射到 `.notdef`（0 号）的码位滤掉了，但**轮廓为空**的字形仍会被计入。它确实有映射，也确实是那个字形，只是画不出内容。所以覆盖率 100% 不等于每个字都好看。
2. **变体序列不算**。`cmap` 里的变体选择符（`U+FE0E` / `U+FE0F` 那类）不在码位区间里，所以 emoji 的彩色版本这种能力看不出来。
3. **只探测、没解析的本机字体没有覆盖率**。这类条目的 `cmapRanges` 是 `null`，页面拿不到区间，只能显示未分析。

## 为什么不用重跑 {#why-live}

如果覆盖率要在服务端算好存下来，就得为每个字体 × 每个区块存一行，数据量随字体数线性增长，而算法本身是一次遍历。现算更简单，也不会因为 Unicode 更新区块表而让旧数据对不上。

代价是每次打开页面都要计算一遍。实测 353 个区块、每个几百个区间，在浏览器里是毫秒级。
